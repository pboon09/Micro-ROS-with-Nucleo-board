# Tips, tooling and troubleshooting

Practical notes for working with this template. They cover what to keep out of
git, how to lay out the workspace, and the common gotchas when bringing a board
online.

## Git ignore rules

STM32CubeIDE and the micro-ROS build produce large, regenerable output that does
not belong in version control. The template ships a ready-made
[`uros_example/.gitignore`](../uros_example/.gitignore) covering the folders
below.

```gitignore
/Debug/                                                         # build output
/Release/                                                       # build output
/micro_ros_stm32cubemx_utils/microros_static_library_ide/libmicroros/   # generated micro-ROS lib
```

`Debug/` and `Release/` are recreated on every build. `libmicroros/` is
regenerated by the Docker pre-build step and is tens of MB.

## Delete the committed Debug folder

The upstream repo committed a `Debug/` folder before the `.gitignore` existed.
A `.gitignore` does not untrack files that are already committed, so you remove
it once with one of the two commands below.

To stop tracking it but keep the files on your disk, use `--cached`.
```bash
git rm -r --cached uros_example/Debug uros_example/Release
git commit -m "Stop tracking generated build output"
```

To delete it from both the repository and your disk, drop `--cached`.
```bash
git rm -r uros_example/Debug uros_example/Release
git commit -m "Remove generated build output"
```

After this the `.gitignore` keeps the folders from coming back. STM32CubeIDE
recreates `Debug/` locally on the next build, and it stays untracked.

## Vendoring micro_ros_stm32cubemx_utils

If you want to commit the `micro_ros_stm32cubemx_utils` folder into your own
repository, remove its upstream git history first so it does not become a nested
repo or submodule.

```bash
cd uros_example/micro_ros_stm32cubemx_utils
rm -rf .git*
```

## Workspace organization

Keep firmware out of the way of `colcon` so it does not try to build your STM32
project as a ROS 2 package.

1. Create a `firmware/` folder in your ROS 2 workspace.
2. Place the STM32 micro-ROS project inside it.
3. Drop a `COLCON_IGNORE` marker so `colcon build` skips it.

```bash
touch firmware/COLCON_IGNORE
```

## Docker permissions

The STM32CubeIDE pre-build step calls Docker without `sudo`. Give your user
access once.

```bash
sudo usermod -aG docker $USER
newgrp docker            # or log out and back in
docker run hello-world   # must succeed without sudo
```

For a one-off alternative that resets on reboot, open the Docker socket.
```bash
sudo chmod 666 /var/run/docker.sock
```

## Match the serial baud rate

The agent's `-b` flag must equal the firmware's LPUART baud rate, which is
2000000 in the template. A mismatch shows up as the agent never establishing a
session.

```bash
ros2 run micro_ros_agent micro_ros_agent serial -b 2000000 --dev /dev/ttyACM0
```

## Troubleshooting

### Agent connects but ros2 topic list is empty

This is usually `ROS_LOCALHOST_ONLY`. When `ROS_LOCALHOST_ONLY=1`, DDS is
restricted to localhost and the agent's nodes become invisible to the rest of
ROS 2, even though the serial link works. Check and clear it.

```bash
echo $ROS_LOCALHOST_ONLY      # check the value
export ROS_LOCALHOST_ONLY=0   # or run: unset ROS_LOCALHOST_ONLY
```

Also confirm both sides share the same `ROS_DOMAIN_ID`, which the firmware sets
to 127, and a consistent `RMW_IMPLEMENTATION`.

### The _gettimeofday warning

If the build prints `warning: _gettimeofday is not implemented and will always
fail`, add this stub to `Core/Src/syscalls.c`.

```c
int _gettimeofday_r(struct _reent *ptr, struct timeval *tv, void *tz) {
    (void)ptr;   // Unused
    (void)tv;    // Unused
    (void)tz;    // Unused
    errno = ENOSYS;  // "Function not implemented"
    return -1;
}
```

### Nothing appears at all

Press the board's reset button after starting the agent. The device only
establishes the session on boot if the agent is already listening.

### Pre-build fails with a Docker permission error

Your user cannot reach the Docker daemon. See
[Docker permissions](#docker-permissions) above.
